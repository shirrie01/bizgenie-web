## What changed
* `src/premium/insightsClient.js` (replaces the gate-only stub): `makeInsightsApi` over `POST /customer/insights/snapshots`, `POST|GET /recommendations`, `POST /feedback`, `POST /objectives`. Errors follow the contract: unavailable (503 LEARNING_UNAVAILABLE), evidence no longer current (409 EVIDENCE_UNAVAILABLE), stale version (409 VERSION_CONFLICT), key reuse (409 IDEMPOTENCY_KEY_CONFLICT), owner-only/other-tenant (404). A write that may have taken effect is never reported as "nothing was recorded".
* `PremiumInsights`: **nothing is read or stored until the owner asks** (a snapshot is a stored record, so it is created only by the "Read the latest platform results / Refresh results" button, owner only; there is no read route for the latest snapshot). Members read the shared suggestions list. The owner can "Look for a change" between the two most recent periods of one measure (`snapshot_id`, `previous_id`, `current_id` from the snapshot just read); a decision carries the server's `feedback_version` as `expected_version` and one idempotency key per decision; a decision the server already holds is shown as saved with no buttons; an `invalidated` decision says it no longer applies and cannot be re-decided.
* `src/intel/performanceEvidence.js`: reads `snapshot_id`, the `unavailable` reasons `source_unavailable` / `limit_exceeded`, and the recommendation's `decision` / `feedback_version`. New snapshot rows are canonical (`performance-observation.v1`, accepted); older persisted rows without the row version are accepted as history (unit-tested); a wrong row version is refused.
* Recommendations stay "observed change only": no cause, no forecast, nothing changes unless accepted, and an accepted decision changes no Brand Brain or campaign.

## Not wired / not proven
* `GrowthCentre`'s "objective" is the business goal in the customer's words; it is not the backend's campaign performance objective (objective id + metric + version). Mapping them would be a guess, so `configureObjective` exists in the client and is integration-tested but has **no screen** yet. It needs a design decision.
* No public ingestion route exists, so no real platform data can reach this screen until trusted connectors and dictionaries are supplied (backend/Meta, external). Scheduling of snapshot creation is also absent.
* Currentness is a point-in-time read; every write can still answer 409.
