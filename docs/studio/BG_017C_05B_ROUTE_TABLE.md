# BG-017C-05B — Shared route table (Studio ↔ trusted staging bridge ↔ frozen launch contract)

7 Nov 2026. Answers the request on API PR #229 (comment 6708228889): one table of every API route the Studio can call, with method, purpose, whether the trusted staging bridge carries it, auth, cost/write risk, the launch class against the frozen first-paying-customer contract (Issue #128), and the owner. Claude owns the Studio-side inventory and the "not available" wording; Codex owns the routes. **The "In the bridge" column is computed** from the vendored bridge route table (Codex PR #229 head `6adeed03`, `src/studio-bridge/service.js`), and a test fails if the table, the Studio's call sites or the bridge extract drift apart. The classes are **proposals for Codex and the founder to confirm**, not decisions.

Launch classes: **A** mandatory first-paying-customer operation · **B** required, but through a separate first-party secure route with its own approved contract · **C** explicitly deferred or disabled, with truthful Studio wording · **E** extra, not needed for the first paying customer.

## Result in one paragraph
Of the 63 routes in 29 rows, every mandatory (A) route except one is carried by the bridge. **The exception is `POST /billing/stripe/checkout`** (outside `/customer/`): without a verified secure route for it, a customer cannot pay (#128 L4), so it cannot be deferred for a paid launch. It needs a narrowly reviewed, tenant-bound, owner-only route with a threat model (Codex) and an approved plan/price (founder). Until then a bridge-pointed Studio build says "Subscribing isn't available in this test environment yet, so nothing can be charged" and calls nothing. Manual publication is class C pending a founder decision on whether it is part of the first paying customer's journey. Billing management/invoices, insights, uploads, social writes and the provider OAuth callback are deferred (C), with the callback needing a separate decision because it is an unauthenticated provider redirect that must reach the API host and not the bridge.

## How the Studio behaves where the bridge does not carry a route
- A build whose API origin is a listed bridge origin (`BRIDGE_API_ORIGINS` in `studio-staging-release.yml`, empty today) is marked `VITE_API_ROUTE_LIMITS=bridge-v1`. Then Stripe checkout and manual publication make **no request** and say they are not available in this test environment yet, and that nothing was charged or changed. Features behind a build gate that is off (billing management, insights, uploads, plan catalogue, credit preview) are not shown at all.
- Nothing is added to the bridge by the Studio, and no endpoint is invented. Codex proposes any new route and its threat model on PR #229; the Studio then adds the route to this table and removes the limit.
